# Backend Architecture Guidelines

This is the `server/` analog of `00-overview.md`'s "Locked-in stack decisions": a record of what was decided for the Go/Redis/Postgres backend and, more importantly, *why* — so a future session or contributor extending `server/` has a stated default to build on instead of re-deriving these choices per feature, and so a reviewer can check a change against the reasoning it's supposed to follow, not just the outcome.

Read `00-overview.md` first for the project-wide framing. This doc assumes that context and covers only what's specific to the backend.

## Locked-in backend decisions

### Data layer

| Decision | Choice | Why |
|---|---|---|
| Primary datastore | **Redis + Postgres hybrid**. Redis for the atomic operations on bidding (super important and takes away the headache of race conditions). Postgres for the filtering/sorting and non-volatile audit trail. | I was going to do Redis-only but Postgres makes filter/sort/pagination so much easier than hand-rolling in Redis |
| Redis persistence | `appendonly yes`, `appendfsync always` (not the default `everysec`) | At this system's realistic bid volume the fsync cost is negligible. With this setup we can make sure to recover state in case Redis ever crashes |
| Redis key naming | Hash-tag braces on a listing's keys: `{listing:<id>}:state`, `{listing:<id>}:stream` | Costs nothing single-instance; keeps a listing's keys co-located and scriptable together if this ever moves to Redis Cluster. |
| `auction_duration_sec` | Stored a duration for the auction instead of an auction end time. | This makes it easier to implement an anti-sniping measure later where we can easily increase the duration of an auction when a new bid comes in at the last moment. |
| `status` (`upcoming`/`active`/`ended`) | Never a stored column — computed at query time from `auction_start`/`auction_end` vs `now()`, using the same predicates that back the "ending soonest" sort ordering (`internal/platform/pgstore`). | A stored `status` column would go stale the instant time passes unless a background job kept touching every row. Computing it at query time is always correct with zero upkeep, and reuses the same indexes the sort already needs — one pair of indexes serves both the filter and the sort. |
| `reserve_price` | Fully stored and queryable in Postgres. Excluded only from the buyer-facing `ListingSummary` DTO (`internal/transport/dto`) — the Go struct has no such field, not a `null` value. | I don't know what this is for but I know it might be useful for backwards compatibility or business logic that I don't know about yet. We store it but it's not accessed anywhere. |

### API design

| Decision | Choice | Why |
|---|---|---|
| Versioning | Path-based (`/v1/...`) | Simpler, URL-visible, debuggable by inspection — this API has no need for the subtlety header/content-negotiation versioning buys. |
| Health check path | `/healthcheck`, unversioned | Naming preference over the more common `/healthz` shorthand; unversioned because orchestrators/load balancers hit it and don't care about API versioning. |
| Error envelope | `{ "error": { "code", "message", "details", "request_id" } }` on every 4xx/5xx | `request_id` is a trace id used across all three systems for debugging. `code` strings from the Redis Lua layer (`bid_too_low`, `auction_ended`, etc.) act as machine-legible error codes. |
| Status codes | 400 malformed request; 404 doesn't exist; 409 well-formed request rejected by resource *state*; 429 rate-limited; 500 unexpected | 409 specifically for bid-too-low/lifecycle rejections: the request was valid when the client built it, the world (price, lifecycle) moved before it arrived — that's a state conflict, not bad input. |
| Computing `viewer` (`has_bid`/`is_high_bidder`/`is_outbid`) on a listing | `is_high_bidder` is a plain column comparison (`listings.high_bidder_session_id = current_session`) — already denormalized onto the row, no join. `has_bid` is answered from Redis: the Lua accept path `SADD`s the listing id into `session:<token>:bids` on every accepted bid, so a list-page request does one `SMEMBERS` call regardless of page size and intersects it against the page's ids in Go. `is_outbid` is `has_bid && !is_high_bidder`, computed in Go. | These could be values that are computed per query at the db-level but I wanted to avoid the unnecessary JOINs. They complicate queries and make it harder to scale. |
| Idempotency | **No client-supplied idempotency header.** Derived entirely from data already in the request: `(session_id, listing_id, amount)` for a bid, `(session_id, listing_id)` for buy-now. | Used this instead of a uuid because we have a naturally collision-free key: a real auction only accepts a *strictly increasing* price, so the identical `(listing, amount)` pair can never legitimately be accepted twice in a row for one session — the moment the first is accepted, that amount becomes `current_price`, so a second attempt at it is now below the new minimum and would be rejected on its own merits. 
| `viewer` on a bid/buy-now acceptance response | A fixed constant (`has_bid`/`is_high_bidder` true, `is_outbid` false), never a fresh lookup | Whoever's bid or buy-now was just accepted is unconditionally the new high bidder — that's what "accepted" means, so there's nothing to look up. This also isn't optional: an identical retried request must return a byte-identical response to the original acceptance (see Idempotency above), and a live Redis lookup on replay could disagree with that if someone else has since outbid this session in the time since. The response describes the accept event itself, not a live snapshot of the listing. |
| Buy-now guardrail | Reject with `409 buy_now_unavailable` once `current_price >= buy_now_price` | New rule — today's client never needed it (no rival bidder to race against), but a real concurrent-bidder backend does: someone can now out-bid past the buy-now price before another session clicks it. |
| `total_count` on list responses | Omitted by default | An extra `COUNT(*)` on every list request isn't worth it for an infinite-scroll UI that can show "N loaded so far." Revisit as an opt-in query param if a future UI genuinely needs a literal "X results" count. |
| `GET /v1/listings/{id}` freshness | Reads Postgres only, no Redis overlay for zero-lag price | Keeps this endpoint uniform with the list endpoint and consistent with keeping stateless reads portable to a different transport later. Anyone actively viewing a listing gets true-live updates via the WebSocket regardless — this endpoint only serves the initial snapshot. |

### Pagination

| Decision | Choice | Why |
|---|---|---|
| Pagination style | Cursor/keyset, not `OFFSET/LIMIT` | Naive offset pagination skips/duplicates rows exactly when a sort key changes between page loads — a bid changing `current_price`, or time passing during an "ending soonest" sort. That drift is a real, not hypothetical, failure mode for this dataset once bidding is live. |
| Cursor shape | Opaque `base64url(JSON)` carrying `{sort, fingerprint, bucket, v, id}` | `fingerprint` hashes the active filter+sort params (not page size or direction) so switching those mid-walk from an existing cursor still works; a mismatch is a `400 cursor_sort_mismatch`, preventing silent pagination over a different filtered set than the cursor was issued against. |
| Tiebreak | Every sort mode orders by `(primary_column, id)` | Ties on `price`/`year` are real with 200 rows; without a tiebreak the order isn't deterministic across page loads. |
| "Ending soonest" sort | Three buckets (active by `auction_end ASC`, upcoming by `auction_start ASC`, ended by `auction_end DESC` as a tiebreak), queried in sequence, not a single `ORDER BY` expression | Reproduces the client's existing 3-tier `sortKey()` comparator exactly, using absolute indexable timestamp columns instead of a `now()`-relative expression a btree index can't back. The ended-bucket tiebreak is new — the client's original comparator never actually ordered ended listings among themselves. |
| `OFFSET/LIMIT` | Not used | Available as a simpler fallback if a future maintainer decides the drift is an acceptable cosmetic glitch rather than a correctness problem — not this design's choice to make unilaterally, so it's noted rather than silently ruled out forever. |
| Cursor timestamp encoding | `time.RFC3339Nano`, not `time.RFC3339`, for the `auction_start`/`auction_end` cursor `v` | **Deviation on record**: `RFC3339` has no fractional seconds, but Postgres `timestamptz` carries microsecond precision. Encoding a row's timestamp with `RFC3339` truncated it to the whole second, so the decoded value came back strictly *before* that row's actual stored value — a `>` keyset predicate against the truncated cursor stayed true for the very row the cursor was issued from, re-including it on the next page instead of excluding it. Caught by the "ending soonest" bucket-crossing integration test, not by inspection. |

### Realtime / WebSocket

| Decision | Choice | Why |
|---|---|---|
| Connection model | One multiplexed WS connection per client, subscribing to a set of listing ids (not one socket per listing) | Matches the existing Watchlist reality — a user watches many listings at once via the client's watchlist feature. |
| Viewer-relative fields (`high_bidder_is_you`) | Computed per recipient connection by the Hub, not baked into the broadcast event | The same underlying accepted-bid event means something different to each subscriber (whether they're the high bidder), so it has to be resolved per connection at send time, using the session the Hub already resolved at upgrade. |
| Fan-out mechanism | `Broadcaster` interface (`internal/usecase/realtime`); `inmemory.Broadcaster` shipped today; a Redis Pub/Sub implementation is a config-flag swap (`BROADCASTER_MODE=redis-pubsub`), not built yet | Only one server instance runs today, so in-process fan-out is correct and simplest. The interface exists now specifically so a second instance doesn't require a rewrite, just a new adapter. |
| Draining vs. broadcasting | Two distinct roles off the same Redis stream: draining wants competing-consumers semantics (each entry processed once, by whichever worker); broadcasting wants every instance to hear every event. Handled today by one in-process "stream tailer" doing both jobs via a plain checkpointed `XREAD` (not a consumer group). | Consumer groups only earn their complexity once the drain role is split across multiple worker replicas — not the case yet. A checkpointed `XREAD` resuming from `listings.last_event_stream_id` (stored in Postgres) is sufficient for crash recovery with fewer moving parts. |
| Gap-free reconnect (replay missed events via `XRANGE` from a client-supplied checkpoint) | Deferred | Streams make it cheap to add later; not building it now keeps v1 simpler. Tracked in the root `README.md`'s "What I'd Do With More Time." |
| `listing_ended` push for natural time expiry | Not sent. The stream tailer only ever publishes `listing_ended` for a Buy Now (`reason: "bought_now"`). | Time passing isn't an event anything "does" -- every connected client can already derive `auction_end` has passed on its own, exactly like the existing client's `clock` store does today (`deriveLifecycle`). Proactively pushing that too would mean a new background job scanning for newly-expired listings, which nothing in this design calls for -- Buy Now is the one case with no other way for a viewer to find out, so it's the one case worth a push. |
| `XReadArgs.Block` on the stream tailer's poll | Explicitly `-1` | **Caught by a hung test, not by inspection**: go-redis only omits Redis's `BLOCK` argument when `Block < 0`. A bare struct literal's zero value, `Block: 0`, is `>= 0`, so go-redis sends a literal `BLOCK 0` to Redis -- which means "block forever," not "don't block." The very first `Tick()` call in `TestStreamTailer_DrainAndRestart` hung for the full 11-minute Go test timeout before this was set explicitly. Worth remembering for any future code that touches `XReadArgs`: the zero value is not "no blocking," it's "block forever." |
| Subscription cap | 100 listing ids per connection (`ws.MaxSubscriptionsPerConnection`) | Bounds one connection's fan-out cost and the Broadcaster's per-listing subscriber map size. A `subscribe` request that would exceed it is accepted up to the cap (the ack reflects the connection's actual, capped set) plus a `subscription_cap_exceeded` error message -- never a hard connection close for what's more likely a client bug than an attack. |
| Keepalive | Server ping every 30s; a connection with no frame (pong or otherwise) for 60s is considered dead | 60s is a generous multiple of the ping interval so one delayed pong (a slow client tab, a network blip) doesn't kill a healthy connection. Detects a connection Caddy or an intermediate proxy silently dropped without a clean close frame. |
| `wireWriter` seam (`ws.Connection`) | `Connection` holds a narrow one-method interface (`WriteJSON`) instead of a concrete `*websocket.Conn` | `*websocket.Conn` satisfies it structurally with zero adapter code, but the seam is what makes `Connection`'s own logic (subscription bookkeeping, translating a `realtime.Event` into this recipient's wire message, computing `high_bidder_is_you`) unit-testable with a fake writer -- no real network socket needed for any of that. The Hub's own upgrade/protocol-loop behavior is still tested against a real `httptest.NewServer` and a real client dial, since that's the only way to exercise an actual HTTP-to-WS upgrade. |
| `statusRecorder.Hijack` (AccessLog middleware) | Added a `Hijack` passthrough to the access-log wrapper | **Caught by building the WS upgrade path, not by inspection**: `statusRecorder` (added in an earlier commit, before any WS code existed) embeds `http.ResponseWriter` as an interface field to capture the status code. Embedding an *interface* only promotes that interface's own methods (`Header`/`Write`/`WriteHeader`) -- not `http.Hijacker`'s `Hijack`, even though the real `*http.response` underneath supports it. `gorilla/websocket`'s `Upgrade` asserts for `http.Hijacker` on whatever `ResponseWriter` it's handed, so without this fix, every single WS upgrade request would have failed the instant it passed through `AccessLog` -- silently, since nothing about GET /v1/listings or any other existing route ever needed `Hijack` to notice the gap. Fixed here rather than by routing `/v1/ws` around `AccessLog`, since losing access logs for the one route that most needs connection-lifecycle visibility would be the wrong tradeoff. |
| WS Origin check | Allow-list on upgrade | `SameSite` cookie attributes don't reliably cover the WebSocket handshake, so the Origin header is checked explicitly as a second layer. |

### Sessions & security

| Decision | Choice | Why |
|---|---|---|
| Session identity | Opaque token, `base64url(32 crypto/rand bytes)` — not a JWT | Nothing worth encoding client-side; it's purely a server-side lookup key. Also the audit trail's bidder identity (opaque, not PII). |
| Cookie attributes | `HttpOnly`, `Secure`, `SameSite=Lax`, **no `Max-Age`/`Expires`** | `HttpOnly`/`Secure` block XSS theft and require HTTPS. Omitting `Max-Age` deliberately: the *actual* sliding TTL lives entirely in Redis's `EXPIRE`, refreshed on activity. Giving the cookie its own `Max-Age` in addition would create two independent clocks disagreeing about session validity (a cookie that outlives its Redis record, or vice versa, depending on which one drifts) — Redis stays the single, unambiguous source of truth for whether a session is still valid. |
| CSRF | `SameSite=Lax` as the primary defense, plus a required custom header (e.g. `X-Requested-With`) on state-changing requests | A malicious cross-site page placing a griefing bid as an unwitting visitor's anonymous session is a real abuse vector even without login. A simple cross-site form/request can't attach a custom header, so requiring one is a cheap second layer. This is also why Caddy proxies the client and the API under one origin — a cross-origin split would force `SameSite=None`, which removes the primary defense. |
| `/healthcheck` and Session/CSRF | `/healthcheck` is registered outside the `Session`/`CSRF` part of the middleware chain (still gets request id/panic-recovery/access-log) | An orchestrator's liveness/readiness probe hits this path every few seconds. Routing it through `Session` would `Touch` a brand-new Redis session (and a `Set-Cookie` header on the response) on every single ping — wasted writes and pointless key churn for a request that will never come back to use that session. `router.go` splits the mux instead of adding a per-route opt-out flag: `/healthcheck` is registered on its own minimally-wrapped handler, everything else falls to the fully-wrapped catch-all, and Go 1.22 `ServeMux`'s own pattern-precedence rules (an exact match beats `"/"`) make the split deterministic. |
| Rate limiting | Fixed-window counter per session, per bid-relevant endpoint | Mitigates abuse without needing real auth first. |

### Deployment & HTTPS

| Decision | Choice | Why |
|---|---|---|
| TLS termination | Caddy (a reverse-proxy container), not the Go binary itself | The Go binary speaks plain HTTP/WS internally and never contains TLS-handling code — this mirrors what a cloud load balancer/API Gateway would do in front of it later, so the application code doesn't change across deployment targets. Caddy's automatic-HTTPS behavior (local cert via `mkcert`, or automatic ACME for a real public hostname) needs near-zero config either way. |
| Same-origin client + API | Caddy reverse-proxies both the client and `/v1/*` under one origin (`https://localhost` locally) | Required for the `SameSite=Lax` cookie (and the CSRF defense built on it) to work at all — a cross-origin split would force `SameSite=None`. |
| Local HTTPS trust (Windows 11) | Scripted (`deploy/docker/setup-ssl-windows.sh` / `cleanup-ssl-windows.sh`), not prose instructions | `mkcert -install` is a host-level trust-store operation Compose can't perform. `cleanup-ssl-windows.sh` always removes the generated project cert/key, but never runs `mkcert -uninstall` (which affects the *entire machine's* trust store, not just this project) unless an explicit `--uninstall-ca` flag is passed. The *first* `mkcert -install` on a machine triggers a Windows UAC elevation prompt (installing into the system trust store needs admin rights) -- expected, not a hang, but it does mean this script can't complete unattended/non-interactively the very first time it runs on a given machine. Verified end-to-end against a real browser (not `curl.exe`, whose Windows build uses the schannel TLS backend and fails locally-issued certs on an unrelated revocation-check quirk, `CRYPT_E_NO_REVOCATION_CHECK` -- not a sign anything here is wrong, just that backend's own strictness). |
| Dataset reconciliation on startup | One-shot Compose init service (`cmd/reconcile`), gated via `depends_on: condition: service_completed_successfully` before `app` starts, on *every* `docker compose up` | See "Data lifecycle" below. |
| One image, two binaries | A single multi-stage `Dockerfile` builds both `cmd/api` and `cmd/reconcile` into the same runtime image; `docker-compose.yml`'s `app` and `reconcile` services pick which one runs via `command:` | They share one Go module and rebuild together anyway -- a second image would double the build time for no isolation benefit, since neither binary is ever deployed independently of the other's build. |
| Dockerfile `ENTRYPOINT` | None -- `CMD ["api"]` only. Each service's own `command:` (`["api"]` / `["reconcile"]`) is the full executable line, not an argument to something else. | **Caught by actually running `docker compose up`, not by inspection**: an earlier version set `ENTRYPOINT ["api"]`, expecting each service's `command:` to choose the binary. Docker doesn't work that way -- `ENTRYPOINT` and `CMD`/`command:` *concatenate* (the entrypoint is the executable, the command supplies arguments to it), so `reconcile`'s `command: ["reconcile"]` actually ran `api reconcile` -- the long-lived API server, silently ignoring the extra argument. That's why the `reconcile` container never exited and `app` (waiting on `service_completed_successfully`) never started at all. |
| Vehicle dataset mount | `data/vehicles.json` is bind-mounted into `reconcile` (`../data:/data:ro`), never `COPY`'d into the image | The reconciliation feature's whole point is that regenerating the dataset on the host and re-running `docker compose up` picks up new listings without a rebuild (D5/§10) -- baking it into the image at build time would defeat that. |
| Client in Compose | A stock `node:24-alpine` image runs the existing `npm run dev -- --host` as-is (no client-specific Dockerfile), reachable through Caddy at `/` | Client integration is a later phase (this repo's own commit sequence) -- the client doesn't call this API yet. This exists purely so "one origin for client + API" is provable end-to-end now, not to containerize the client for real; a production client image (a build step + a static file server) is a later concern once the client actually depends on this backend. |

### Data lifecycle (dataset regeneration)

| Decision | Choice | Why |
|---|---|---|
| Reconciliation strategy | Insert-only-new, by id: `INSERT ... ON CONFLICT (id) DO NOTHING` from `data/vehicles.json` into `listings`, on every startup. Never updates an existing row's fields, never deletes a row missing from the generated file. | The vehicle dataset may be regenerated over time (a bigger run, a tweaked generator) and re-synced into a stack that already has real bids against some listings. A blind re-seed would destroy that live state the moment the generated output changes at all. Letting Postgres's own conflict handling be the "already exists" check (rather than a `SELECT`-then-diff in application code) also makes this race-safe against two reconcile runs. |
| Redis state priming | For every listing row in Postgres (not just newly-inserted ones), `HSETNX`-prime `{listing:<id>}:state` from that row's own current fields if the Redis key is missing | One pass covers both a brand-new listing (Postgres has `current_price = starting_bid`) and a Redis-data-loss recovery scenario (Postgres already reflects real bidding, so priming from it restores true state instead of resetting it). This is what makes Redis fully disposable/reconstructable — Postgres is the only store that has to survive for the system to recover correctly. |
| Vehicle-generator seed | `scripts/generate_vehicles.mjs` defaults to a `Date.now() + process.pid`-derived seed; accepts `--seed=<n>` to reproduce a specific run on demand, including its ids | **Deviation on record, twice over**. First: the generator originally hardcoded `mulberry32(42)` — revised so re-running it ordinarily produces a genuinely different 200 vehicles, not the same 200 replayed under new ids. Second, a real bug caught by `scripts/generate_vehicles.test.mjs`'s same-seed-same-output test rather than by inspection: `id` was generated via `crypto.randomUUID()`, a source entirely independent of the seeded `rng()` — so even a fixed `--seed` never actually reproduced a prior run's ids, undermining the "reproduce a specific run for a test fixture" reason `--seed` exists at all. Fixed by building the UUID's bytes from `rand()` (`seededUUID()`) instead, so `--seed` now covers every field. |
| `auction_start` timezone interpretation | Parsed as UTC (Go's `time.Parse` default when the layout carries no zone) | The generator's `formatLocalDateTime` (`scripts/generate_vehicles.mjs`) writes `auction_start` using local wall-clock getters (`getFullYear`/`getHours`/etc, not the UTC variants) with no zone marker at all — so the string is really "whatever timezone the machine that ran the generator happened to be in," which is unrecoverable from a committed static JSON file. The client's own `new Date(auctionStart)` has the same latent ambiguity (a browser interprets a zone-less string as *its own* local time, which only matches the generator's original intent if both happen to share a timezone). UTC is simply the only deterministic, environment-independent choice available server-side once the file is just data — not a claim that it recovers the "true" original instant. |

### Logging

| Decision | Choice | Why |
|---|---|---|
| Log output | `log/slog` JSON handler to `os.Stdout` only — no file path, no rotation library, no volume mount for logs | **Deviation on record**: an earlier draft wrote to a file via `lumberjack` (mounted to a Docker volume for persistence). Revised because Docker's own `json-file` logging driver already writes every container's stdout to disk and rotates it (`max-size`/`max-file` in Compose config) — more battle-tested (it's Docker's own core facility, not a third-party library) and removes a dependency entirely. It also collapses what would have been an environment-specific writer switch (file locally, stdout for a hypothetical Lambda) into one code path that's simply correct everywhere. |
| Crash safety | Never wrap the log writer in a `bufio.Writer`; panic-recovery middleware on every handler logs the panic + stack + `request_id` before returning 500 | The point of "crash-safe" is that a crash gets no chance to flush a buffer it doesn't have. A recovered panic still gets logged and still returns a response, rather than silently killing the process. |
| Correlation | `request_id` (per request) and `session_id` (once resolved) thread through `context.Context` via `internal/platform/logging.WithLogger`/`FromContext`, attach to a per-request child logger, echo back as `X-Request-Id` | Each middleware wraps whatever logger it finds in context with `.With(...)` and re-attaches the child, so fields accumulate rather than replace each other -- `request_id` from `RequestID`, then `session_id` once `Session` resolves it, for everything logged downstream of each. |
| Correlating a log line to its durable audit row | The bid/buy-now accept handler logs `bid_id` on its own success line, already carrying `request_id` from the context logger | **Deviation on record**: an earlier draft of this doc said `request_id` "lands in the `bids.request_id` column" -- that column exists in the schema but no write path (the Lua accept scripts, the stream tailer's insert) has ever populated it. Rather than threading `request_id` through the Lua scripts' `ARGV`, the Redis stream fields, *and* the stream tailer's insert just to duplicate a correlation `bid_id` already gives for free (`bid_id` round-trips unchanged from the handler through Redis into `bids.id`), the handler logs both together at the one point they're already both in scope. `bids.request_id` stays in the schema, unpopulated, in case a future write path wants it. |

### Code organization

| Decision | Choice | Why |
|---|---|---|
| Architecture | Hexagonal / ports-and-adapters: `internal/domain` (pure Go) → `internal/usecase/*` (interfaces/ports) → `internal/platform/*` (Redis/Postgres adapters) and `internal/transport/*` (HTTP/WS adapters) | Keeps business logic free of any one transport's or datastore's types, so either can be swapped or added without touching the logic in between. |
| AWS Lambda | **No stub files** (`cmd/lambda`, `internal/transport/lambda` don't exist). `internal/usecase/listings` stays free of `net/http` types and `internal/transport/dto` stays framework-agnostic, so a future Lambda adapter *could* be added easily — but nothing speculative is scaffolded now. | **Deviation on record**: an earlier draft of this design included empty `cmd/lambda`/`transport/lambda` placeholders as part of "Lambda-portability." Revised: that's exactly the kind of premature infrastructure `00-overview.md`'s own Non-goals section already warns against for this repo, just applied to a hypothetical future target instead of a present one. Also worth noting: standard Lambda can't hold a WebSocket connection open the way this backend's realtime path needs — AWS's real answer (API Gateway WebSocket APIs, a connections table, `PostToConnection`) is a different integration model, not a thin adapter swap, so only the stateless `listings` reads are actually designed to port cleanly; the bidding/WS hot path is expected to stay on persistent compute regardless. |
| Router | Stdlib `net/http`'s `ServeMux` (Go 1.22+ pattern routing) | A dozen routes doesn't justify a router dependency; a small `Chain(mw...)` helper covers the middleware-composition ergonomics a library like chi would otherwise buy. |
| Dependency pedigree | Preferred: org-maintained, long track record, wide adoption — ideally a large org (`redis/go-redis`, Google's `google/uuid`), but not at the expense of using something objectively worse. | `github.com/jackc/pgx/v5` is kept as an **explicit exception**: individual-maintained, not org-backed, but the de facto community-standard Postgres driver (the more "org-adjacent" alternative, `lib/pq`, is in maintenance-only mode per its own README). `github.com/gorilla/websocket` was chosen over the more modern, context-aware `coder/websocket` specifically for its much longer production track record, once "battle-tested, years of updates" was the stated bar. `github.com/golang-migrate/migrate` is org-maintained with ~8+ years of adoption. No log-rotation dependency at all (see Logging above). |
| Session-bid tracking | `session:<token>:bids` (a Redis Set), `SADD`ed by the Lua accept path on every accepted bid | Backs the join-free `viewer.has_bid` computation (see API design above) — this is the one piece of state that exists purely to make that lookup cheap. |

## Go conventions (this project's analog of `01-code-conventions.md`)

1. **Typed results at use-case boundaries, not panics.** A use-case function that can be rejected (`PlaceBid`, `BuyNow`) returns a typed result/error, never panics past its own boundary — the same "fail loud in dev, fail safe in the caller" philosophy the client's stores already use for `{ok, error}`.
2. **Sentinel errors in `internal/domain/errors.go`**, wrapped with context via `fmt.Errorf("...: %w", ...)`, never a bare `errors.New` scattered at the call site — one vocabulary of "what can go wrong" for the whole backend, matching how the Redis Lua layer's `error` codes and the HTTP error envelope's `code` field all trace back to the same strings.
3. **Ports are named for what they do, not what they wrap** (`ListingReader`, `BidStore`, `Broadcaster`) — a future adapter (a different cache, a different queue) implements the same interface without the name implying "this is specifically Redis."
4. **`gofmt` and `go vet` are a real gate**, run before every commit alongside `go test ./...` — the Go-side equivalent of the client's `npm run lint` gate.
5. **Comments explain why, not what** — same rule as `01-code-conventions.md`, unchanged. A Lua script or SQL query with a non-obvious constraint (why `ON CONFLICT DO NOTHING` instead of a `SELECT`-then-insert, why `auction_end` reads from Redis `TIME` and not an app-supplied timestamp) gets a one-line comment; straightforward code doesn't.

## Non-goals (for now)

- **User authentication or access control.** Sessions are identifiable (an opaque token), not authenticated. No login, no accounts, no per-user authorization. SOC2-flavored security principles (encryption in transit/at rest, audit trail integrity, least-privilege network exposure) apply regardless — see the plan's SOC2 mapping — but "who is this, really" is out of scope.
- **A `Seller` entity, seller accounts, or seller-facing endpoints.** `selling_dealership` stays a free-text string, matching the client's existing model. `reserve_price` is stored precisely so a future seller-facing surface has real data to build on, but no such surface exists yet.
- **WebSocket gap-free reconnect.** Deferred, see Realtime table above.
- **Multi-instance deployment.** The `Broadcaster` interface and Redis's role as a coordination layer are designed to support it, but only a single `app` instance is actually run today — no consumer groups, no Redis Pub/Sub adapter is built yet.
- **A Lambda deployment target.** See "AWS Lambda" above — designed to be portable for stateless reads, not built.

Keep this list short and revisit it as the backend matures — the same principle `00-overview.md` states for the client applies here too.
